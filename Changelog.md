## [v1.7.1] - Emergency Hotfix

### 🪲 Bug Fixes
- [Bugfix] **Eclipse Endgame Bosses' Shield Scaling Landed as a Flat +25 HP Instead of ~26x-42x (eclipse_boss_scaling.lua):** The boss shield multiplier went through `CosmicVaultBuffs.applyPermanentFactor`, which wraps `entity:addMultiplyableBias` — a flat bias added *before* multipliers are considered, not a percentage (confirmed against the engine's own `Avorion Stubs/Entity.lua` doc comment, and against this workspace's `Avorion_Modding_Codex.md`, which is corrected in the same pass — see below). Passing `shieldFactor` (25.0 or higher) there added a negligible flat shield HP bonus instead of the intended massive multiplier, leaving Eclipse bosses far squishier than the mod's own stated design ("strictly stronger than War Dreadnoughts which get 10x shields"). Switched to `CosmicVaultBuffs.addPermanentBaseMultiplier`, which wraps the correct `entity:addBaseMultiplier`, matching Cosmic War's own established boss-shield-scaling precedent.

### 📖 Codex
- [Correction] **`Avorion_Modding_Codex.md` Recommended the Wrong Primitive for a Percentage Buff, in Three Places:** The Codex's "Shields: never touch `shieldMaxDurability` directly" entry, its `entity.damageMultiplier` entry's code example, and its Quick-Reference table all recommended `entity:addMultiplyableBias` for what they explicitly labeled a percentage buff or DPS lever — directly contradicting the Codex's own correct "Common trap" callout a few lines above the first of these. This is very likely why the bug above existed in the first place. All three corrected, and a new entry added on `entity:removeScriptBonuses()`'s actual (non-self-scoped) behavior, confirmed independently across three live bugs fixed in this same patch (see Cosmic Vault and Cosmic Starfall's changelogs).

## [v1.7.0]

The Eclipse: Crisis Horror Expansion. This release combines a full, file-by-file audit and
bugfix pass across the entire mod (all 62 scripts) with new content built on top of it — what
started as a bugfix-only pass (originally tracked as v1.6.3) grew into a minor version once real
new features were added, so everything below ships together as one release rather than two.
The audit specifically targeted the recurring player reports that the Guardian-kill → Aegis mail
→ Eclipse endgame handoff sometimes never triggers at all, even after hours of play. The v1.6.2
self-healing fixes to `eclipse_awakes.lua` were confirmed correct and left untouched; this pass
found three additional, independent bugs further downstream in the same chain that could each
cause the identical symptom, plus a number of other confirmed issues elsewhere in the mod,
including two more found during a targeted follow-up pass on items initially flagged for design
review, and a further ground-up re-verification of the Eclipse faction's spawn/expand lifecycle
specifically that found several more. On top of all that, this release adds five new mechanics
building directly on systems the endgame already had, two small extensions to the
sector-annihilation aftermath, a new standalone UI window for checking the Eclipse's status, and
two more bugs found and fixed while building the above. Everything new here reuses an
already-proven pattern from this mod or Cosmic Overhaul rather than introducing a new
architecture — no new engine hooks, no vanilla AI/boarding changes, nothing that touches core
Avorion systems.

### ⭐ Features

- [Feature] **Eclipse Remembers — a personal grudge system:** Killing Eclipse ships now raises a per-player `eclipse_kill_score` (credited in `ca_eclipse_abilities.lua`'s `onDestroyed`, weighted by ship class, attributed to every player physically present in the sector at the kill — the same "who's here right now" pattern `ca_world_eater_manager.lua`'s reward payout already used, avoiding any need for new damage-attribution plumbing). `EclipseConquestManager.expandEmpire()`'s existing 40%-flat Personal Ambush roll now scales its chance (up to 85%) and escort size (`eclipseinvasion.lua` gained an `extraHeavies` parameter, up to +4 heavy-class ships) per player from their own score.
- [Feature] **The Choir — escalating ambient dread:** New rumor lines register progressively at the Eclipse's real state transitions (`the_eclipse_unleashed`, `eclipse_fully_awake`, `eclipse_fallen_empire` — one new shared `ca_eclipse_choir.lua` library, called from `eclipse_awakes.lua` and `eclipse_conquest_manager.lua`), rather than all at once at `initialize()` like the mod's original three rumor lines. This was deliberate after finding `CosmicVaultDialogue.registerLine`'s `conditions` table only checks a fixed, closed set of keys with no custom-predicate support — a naive `conditions = {eclipseAwake = true}` would have been silently ignored (see the new Codex entry on this). A one-shot proximity stinger (new `CaBossAudioHook.triggerAmbientStinger`) now fires the first time a player's own script instance (`ascendancyplayer.lua`'s existing `onSectorEntered`, which already runs on every sector entry) sees them cross into `eclipse_held_territory`.
- [Feature] **The Silent Choir — a named horror unit:** A new galaxy-background tracker (`ca_silent_choir_manager.lua`, same cadence class as the existing Nemesis Hunt system) periodically picks an online player, "sights" them while they're in a loaded sector via a reused `ca_phantom` ship (`EclipseGenerator.createAssassin`) carrying a new `ca_silent_choir_unit.lua` behavior — a whisper, then a vanish — escalating to a real, committed fight after the third sighting. Tracked entirely through `Server():getValue("eclipse_silent_choir")`, no local script state to persist.
- [Feature] **Ascendant Ward — a craftable stealth countermeasure:** A new instant-craft option on the Stellar Forge window (10 Ascendant Matter + 20 Ascendant Scrap, `AscendancyForge.craftWard`) grants a `UsableInventoryItem` (`ca_eclipse_ward.lua`) that suppresses this mod's *own* hunting behavior against the user for 30 minutes: the Personal Ambush roll, Silent Choir targeting (both initial selection and an active hunt's next sighting), and Void Siphon aura targeting (`ca_eclipse_abilities.lua`, player-owned ships only). Deliberately built as a separate interaction rather than routed through the 24-hour weapon-forging queue, which has no existing output path for a consumable and whose `claimWeapon()` type dispatch wasn't safe to extend with a third kind of output. Does **not** suppress vanilla AI faction hostility in general — described to players as evading the Eclipse's own scripted behavior, not blanket invisibility.
- [Feature] **Distress Beacon — cooperative Crusade warning:** When a Fallen Empire Crusade targets a player/alliance sector, every online member of that faction/alliance now receives a Mail alert with the target coordinates, giving a real chance to converge before the consequence lands (an Annihilation/Siege roll only actually executes once someone visits the sector, via the existing `eclipse_pending_annihilations`/`eclipse_pending_sieges` progressive-materialization queue this file already had; a Conquest roll's `CosmicVaultTerritory` contest window is a much tighter 120 seconds, a Cosmic Vault-owned timer this file can't extend).
- [Feature] **Eclipse Wastes — annihilated sectors are now mechanically dangerous, not just foggy:** `ca_delayed_annihilation.lua` already applied permanent Dark Matter Fog and spawned a permanent Obliterator guardian on every annihilated sector; it now also attaches `ca_rift_hazard.lua` (the same shield-drain hazard already used for Dark Sectors near the core), so lingering in the Wastes actually costs something.
- [Feature] **Reclaimed ships:** The same annihilation pass now has a 15% chance to spawn a normal Eclipse Interceptor near where a deleted non-Eclipse, non-player ship stood, titled "Reclaimed &lt;Faction&gt; Vessel" — captured just before deletion, not an attempt to convert the wreck object itself.
- [Feature] **The Eclipse: Command Interface — a new standalone UI window:** A new entity script (`ca_eclipse_interface.lua`), attached to every player/alliance-owned ship via a new `Cosmic Ascendancy\data\scripts\entity\init.lua` override (vanilla's own copy of this file has no named functions, confirmed by reading it directly, so this merges cleanly the same way Cosmic Overhaul's `TrashMan.lua`/`fleetstatus.lua` already do at the identical path). Opened by interacting with your own ship, it shows a tabbed dashboard (Overview / Territory / Threats / Personal) covering everything `/eclipsestatus` reports plus the new personal kill score, Ward status, and Silent Choir sighting info, refreshed live while open. Both surfaces now read the same new shared `ca_eclipse_status.lua` library (`EclipseStatus.getSnapshot()`) instead of independently recomputing the same values — the exact class of bug that let `/eclipsestatus` and the conquest manager's own territory counter drift apart earlier in this same release (see the "Eclipse Could 'Re-Conquer' Its Own Territory" entry below).

### 🪲 Bug Fixes

- [Bugfix] **Cinematic Banners Never Actually Rendered, For Any Caller (`ca_boss_audio_hook.lua`):** `CosmicVaultUI.ShowCinematicBanner` is a server-side entry point (`if not onServer() then return false end`) that already does its own complete server→client relay internally. `CaBossAudioHook.showCinematicBanner` called it from the *client* side, after `triggerCinematicBanner` had already relayed there itself via `invokeClientFunction` — a double-relay that meant `ShowCinematicBanner`'s own guard always failed silently. Every banner this file ever triggered — "THE ECLIPSE AWAKENS", "MASSIVE HYPERSPACE ANOMALY", "BLACK AVORION SIGNATURES DETECTED", every "DOOMSDAY EVENT - N MINS" warning — had never actually displayed. Fixed by calling `ShowCinematicBanner` directly from the server-side trigger function; the client-side wrapper was unnecessary middleman code and has been removed. Found while wiring up The Choir's own proximity stinger, which reused the same (broken) pattern before this was caught. See the new Codex entry on this under UI Development.
- [Bugfix] **`eclipse_conquest_manager.lua`'s New Distress Beacon Mail Had a Placeholder/Argument Mismatch:** Caught and fixed during this same session — `Format("...at (%1%:%2%)..."%_T, tx .. ":" .. ty)` passed one concatenated argument against two placeholders. Corrected to pass `tx, ty` separately.
- [Bugfix] **Story Missions Could Roll Their Own Rendezvous Sector as the Target — Permanent Silent Softlock (all 5 `ca_story1_awakening.lua` through `ca_story5_worldeater.lua`):** Every story mission's `getTargetSector(x, y)` picks a random nearby sector via `MissionUT.getEmptySector`, falling back to `x + random:getInt(-30, 30), y + random:getInt(-30, 30)` if that search fails. That fallback could roll an offset of `(0, 0)` on both axes, making the "target" sector identical to the player's current sector. Since every phase's completion is gated on `mission.phases[N].onSectorEntered`, which is wired to the player's engine-level `onSectorEntered` callback and only fires on an actual sector-*crossing* event, a same-sector target can never be "arrived at" — the callback simply never fires for a sector the player never left. The phase, and everything after it, stalled forever with no error, no crash, and nothing in the log pointing at why. This is a structurally exact match for "the questline just stopped" reports with no other symptom. Fixed in all 5 files: the fallback now re-rolls until at least one axis is non-zero, guaranteeing a genuine sector change. See `Avorion_Modding_Codex.md`'s new "a random rendezvous roll that could target the player's own sector" case study for the general lesson.
- [Bugfix] **Unchecked Boss/Escort Spawns Could Crash Before the "Spawned" Flag Was Ever Set — Permanent Silent Softlock (`ca_story1_awakening.lua`, `ca_story3_vanguard.lua`, `ca_story4_citadel.lua`, `ca_story5_worldeater.lua`):** Each of these missions' boss-spawn phases called `EclipseGenerator.createShip()`/`createStation()` (for the ambush escorts, the Vanguard Juggernaut, the Citadel, and the World-Eater/its escorts respectively) and immediately indexed the return value (`boss.title = ...`, `boss:setValue(...)`, etc.) with no nil-check, *before* the line that sets `mission.data.custom.bossSpawned = true`. Neither the vanilla `Sector():createShip()`/`createStation()` nor this mod's own wrapper is documented as failure-proof, and this exact codebase already has a confirmed precedent of a spawn call returning `nil` (the Aegis-ship-spawn case fixed in v1.6.2). If any spawn in this chain ever returned `nil`, the crash on the very next line meant `bossSpawned` never got set — and since each phase's `updateServer()` bails out immediately with `if not mission.data.custom.bossSpawned then return end`, that phase (and the rest of the mission) was permanently blocked, with the failure surfacing only as an anonymous Lua exception inside `onBeginServer()`, never as a labeled "spawn failed" event. Also fixed the same gap on `EclipseGenerator.applyWorldEaterMultiplayerScaling(boss)` in `ca_story5_worldeater.lua`, which indexed `boss` unconditionally as well. All four files now guard every spawn with `if ship/boss then ... end` before proceeding. See `Avorion_Modding_Codex.md`'s new "an unchecked spawn return value ahead of the flag that gates retry" case study.
- [Bugfix] **Ascendant Crafting Goods Not Registered Until 10 Minutes After the Guardian Died (`eclipsegenerator.lua`):** `EclipseConquestManager.initialize()` (`eclipse_conquest_manager.lua`) is the only place in the mod that registers the "Ascendant Matter", "Eclipse Datacore", and "Ascendant Scrap" custom goods via `CosmicVaultGoods.registerGood()` — but that file only ever gets attached via `Galaxy():addScriptOnce()` inside `eclipse_awakes.lua`'s `eclipse_fully_awake` block, which doesn't flip true until 10 minutes after the Guardian dies. Meanwhile, `ca_eclipse_abilities.lua` — attached to *every* Eclipse ship, including the very first ambush ships spawned within seconds by `ca_story1_awakening.lua`'s Phase 3 — has a death-drop chance for "Ascendant Matter". Any Eclipse ship killed inside that 10-minute window was rolling a drop for a good that didn't exist in the `goods` table yet. Fixed by registering all three goods immediately at `eclipsegenerator.lua`'s module-load time as well (confirmed `CosmicVaultGoods.registerGood()` checks for an existing entry by name and no-ops if found, so this and `eclipse_conquest_manager.lua`'s later call are both safe to run redundantly).
- [Bugfix] **`ca_harvester_loot.lua` Never Actually Attached to Harvester Ships:** `EclipseGenerator.createHarvester()` never called `addScriptOnce` for this file, despite the Changelog previously advertising "Ascendant Matter (dropped by Harvesters)" and every sibling ship-type constructor (`createJuggernaut`) correctly attaching its own loot script. Eclipse Harvesters dropped nothing. Fixed by attaching `ca_harvester_loot.lua` in `createHarvester()`.
- [Bugfix] **Missing `include("faction")` Crash on First Interaction (`ascendancybeacon.lua`, `ca_station_overdrive.lua`):** Both files' `interactionPossible()` calls `checkEntityInteractionPermissions`, defined in vanilla `faction.lua`, but neither file included it. `ca_station_overdrive.lua` is attached to *every* player/alliance station on sector entry (`ascendancyplayer.lua`), so a freshly-built station with no other Cosmic script having pulled in `faction.lua` first would crash on its very first interaction attempt; a newly-placed, never-activated Ascendancy Beacon had the identical problem. Both now correctly `include("faction")`, matching the pattern already used elsewhere in the mod (`ascendancyforge.lua`).
- [Bugfix] **`ca_ascendant_gateway.lua` Wrong Argument Order Silently Dropped the Intended Material:** `PlanGenerator.makeShipPlan(playerFaction, volume, styleName, material)` was called with the `Material` object passed in the `styleName` (3rd) argument slot, with the actual `material` (4th) argument omitted entirely — feeding a userdata value into the plan generator's style lookup and silently falling back to a randomly-selected material instead of the intended Ogonite. Fixed the argument order.
- [Bugfix] **Ascendant Aegis Reactor Wiped Other Mods' Combat Buffs (`ascendantaegis.lua`):** `removeDynamicBuffs()` called `entity:removeScriptBonuses()` on a 15-second cycle (and on uninstall) — this clears **every** script-added stat bonus on the entity, not just this system's own Phase-Shift buff. Cosmic Overhaul's `captainelitetraits.lua` and Cosmic Starfall's `bastionSystem.lua` both apply their own temporary combat buffs to player ships through the same entity-bonus pool, so a ship carrying an Aegis Reactor alongside either of those buffs had the other mod's buff silently erased every cycle. Rewrote to track this system's own two bias keys and call the scoped `entity:removeBonus(key)` instead.
- [Bugfix] **Ascendancy Siege Fleet Spawn Caused a Sector-Wide Collision Pass (`ascendancysiege.lua`):** `Placer.resolveIntersections()` was called with no argument, which defaults to resolving overlaps for *every* BoundingSphere entity in the sector — a needless TPS cost, and a real risk of nudging unrelated entities (the player's own ship, an Ascendancy Beacon) that had nothing to do with the freshly-spawned siege fleet. `ca_darksector_generator.lua` already does this correctly elsewhere in the mod. Fixed by collecting the siege fleet's own spawned ships into an array and passing only that to `resolveIntersections()`.
- [Bugfix] **`is_eclipse` Cross-Mod Compatibility Flag Never Set:** Four files across three sister mods (`Cosmic Overhaul\...\tradecommand.lua`, `Cosmic Vault\...\cv_weather_controller.lua`/`cv_weather_debuff.lua`, `Cosmic War\...\cosmicwartraits.lua`/`siegeevent.lua`) all check `faction:getValue("is_eclipse")` as a fallback for detecting The Eclipse faction, alongside a straight name comparison — but nothing anywhere ever set that value. This was harmless today only because no shipped translation currently changes "The Eclipse"'s displayed name, so the name-equality half of the check always matched; it would have silently broken the moment a localization changed that string. Fixed by setting `is_eclipse = true` in `EclipseGenerator.getFaction()`.
- [Bugfix] **`ca_anomaly_stash.lua` Rarity Roll Didn't Match Its Own Comment:** `random():getInt(1, 3)` was labeled `-- Uncommon to Exceptional`, but per `RarityType` (Common=1, Uncommon=2, Rare=3, Exceptional=4), that range actually rolled Common through Rare. Fixed to `getInt(2, 4)` to match the stated intent.
- [Cleanup] **Dead Includes Removed (`ascendancyforge.lua`):** `PlanGenerator` and `ShipGenerator` were both included but never referenced anywhere in the file.
- [Cleanup] **Short `addScriptOnce` Paths Normalized:** `ca_envoy_despawn.lua` (its own `entity/story/ca_ascendant_envoy.lua` and `delayeddelete.lua` references) and all 5 story missions' Aegis-envoy attachment calls now use the full, unambiguous `data/scripts/...` path form throughout, removing the Linux short-path-resolution risk class this codebase has hit before. No behavior change on Windows; removes a class of risk on Linux dedicated servers.
- [Bugfix] **World-Eater Doomsday Clock Could Wipe a Sector Mid-Fight (`ca_world_eater_manager.lua`):** The 20-minute Doomsday countdown kept ticking down even after a player reached the target sector and the fight actually began — `injectSectorScript()` spawning the boss didn't stop `executeDoomsday()` from still firing once the original clock ran out, silently annihilating the sector (and ending the encounter) out from under an in-progress fight, regardless of how the battle was actually going. No other World-Eater encounter in the mod (the scripted campaign fight, the player-summoned Raid Boss) carries any wipe timer once the fight has started — the 20-minute clock's actual job is to measure whether someone *reaches* the World-Eater in time, not whether they *kill* it in time. Fixed by marking the event `engaged` the moment a player is confirmed present and the fight is injected; once engaged, the countdown (and its warning broadcasts) permanently stop, and the event now only ever resolves via `cancelEvent()` on an actual kill, exactly like every other World-Eater spawn path.
- [Bugfix] **Ethereal Ships Could Become Permanently Invincible on a Sector Reload (`ca_eclipse_abilities.lua`):** `triggerPhaseShift()`'s 4-second invincibility window (Phantom/Interceptor-class ships only) was tracked purely in transient Lua state (`isPhasing`/`phaseEndTime`) with no `secure()`/`restore()` at all. If a sector happened to unload during that exact 4-second window, the ship reloaded with `entity.invincible` still `true` (a real, database-persisted entity property) and no script-side timer left to ever clear it again — leaving that specific ship unkillable for the rest of its lifetime. Also, the genuine once-per-lifetime `hasPhased` flag (Phase Shift is only meant to trigger once per ship, ever) wasn't persisted either, so a reload could let it fire a second time. Added `secure()`/`restore()`: `hasPhased` is now properly persisted, and `restore()` defensively clears `entity.invincible` specifically for Ethereal-class ships (verified this doesn't affect the World-Eater's own independent invincibility management in `ca_worldeater_behavior.lua`, which is a different, non-Ethereal class).
- [Bugfix] **Eclipse Territorial Expansion Silently Suppressed for the First 6+ Hours of Every Galaxy (`eclipse_conquest_manager.lua`):** `expandEmpire()`'s Citadel Suppression Field check defaulted `eclipse_citadel_destroyed_time` to `0` when no Citadel had ever been destroyed, then compared `Server().unpausedRuntime - 0 < suppressionDuration` (a minimum of 6 hours). Since `unpausedRuntime` also starts near `0` for a freshly created galaxy, "no Citadel has ever died" and "a Citadel died at the exact moment the galaxy was created" were indistinguishable — silently suppressing **all** Eclipse territorial expansion (conquest, annihilation, Crusades) for the first 6+ hours of any galaxy's played time, even before the Guardian is ever killed. `eclipse_threat` kept accumulating and got reset every time it crossed 10000 regardless (the suppression check runs after that reset, inside `expandEmpire()`), so this produced no error, no log entry, and no visible symptom beyond "the Eclipse doesn't seem to be doing anything." Fixed by only applying the suppression window once a real Citadel death has actually been recorded (`citadelDestroyed ~= nil`). `/eclipsestatus` (`eclipsestatus.lua`) had the identical default-value bug in its own display logic, reporting "[Citadel Suppression Field]: ACTIVE, halted for 6 hour(s)" on a galaxy that had never had a Citadel die — fixed the same way.
- [Bugfix] **Eclipse Could "Re-Conquer" Its Own Territory, Inflating the Conquered-Sector Counter (`eclipse_conquest_manager.lua`):** The geographic-spread coordinate picker could exhaust all 10 retry attempts without finding an unclaimed sector and silently fall through with the last (already-held) coordinate still set, and neither the Crusade-retarget path nor the known-sector fallback path were ever checked against `eclipse_held_territory` at all. Since `eclipse_conquered_sectors` was incremented unconditionally on every conquest/annihilation regardless of whether the target was already held, this could inflate the counter past the real number of distinct sectors held — throwing off the Fallen Empire threshold (`conqueredCount >= 75`) and `/eclipsestatus`'s reported holdings. Fixed with two changes: the geographic-spread loop now clears its target on total exhaustion instead of keeping a stale duplicate, and a single unified check right before the conquest/annihilation branch (covering all three target-selection paths at once, the same pattern already used for the Sanctuary Field check) bails out for the tick entirely if the selected coordinate is already held.
- [Bugfix] **A Returning Player Who Missed the Guardian's Death AND the 2-Hour Fallback Window Could Never Be Contacted by Aegis (`eclipse_awakes.lua`):** The per-player envoy trigger checked `player:getValue("wormhole_guardian_destroyed")` (only ever set for players physically present at the kill) or `guardian_respawn_time ~= nil` (a reliable fallback, but one that vanilla itself clears ~2 hours after the kill, when the Guardian "respawns"). A player offline for that entire 2-hour window, logging in for the first time only afterward, satisfied neither condition — even though `the_eclipse_unleashed` (this mod's own permanent, non-expiring marker that the Guardian has been killed at least once, ever) was already `true` for the galaxy. That flag was only ever used to gate the one-time galaxy-wide broadcast, never consulted per-player. Added it as a third, permanent fallback condition in the per-player check, so any player who logs in after the galaxy has already awoken gets swept up regardless of how long ago that was or whether they personally witnessed it.
- [Cleanup] **Dead Write-Only Flag Removed (`eclipse_awakes.lua`):** `ca_envoy_spawned` was still being set on every trigger despite being fully replaced by `playerHasAegisProgress()` in v1.6.2 and never read anywhere in the mod since. Removed the now-pointless write.
- [Bugfix] **Eclipse Damage/Stat Scaling Used the Wrong Multiplier Primitive Mod-Wide (`eclipsegenerator.lua`, `ascendantaegis.lua`, `ascendanteclipsebane.lua`, `ca_worldeater_behavior.lua`):** This exact bug pattern — `addMultiplyableBias` (confirmed via vanilla `behemothcarriersystem.lua` to be the ADDITIVE-bias primitive, e.g. "+2 fighter squads") used where `addBaseMultiplier` (the genuine percentage-multiplier primitive, e.g. "+30% production") was needed — had already been found and fixed three separate times elsewhere in this mod (see the "World-Eater DPS Scaling Desync", "Ascendant Gateway DPS Scaling Desync", and "Ascendant Relic Math & API Desync" entries further down this changelog). `EclipseGenerator.applyDamageMultiplier()` — the single shared damage-scaling function called by **every** Eclipse ship's damage bonus (World-Eater 3.0x, Harbinger 10.0x, Phantom 3.0x, Interceptor -0.2x, Defiler 1.5x, plus every Remnant Escalation and multiplayer-scaling layer built on top of it) — had the identical bug and was missed by all three prior fixes, along with 13 further direct `ShieldDurability`/`Velocity`/`FireRate`/`CargoHold` percentage-bonus calls throughout the same file, one inconsistent call in `ascendantaegis.lua` (its sibling `ShieldRecharge` call right next to it was already correct), the "All Damage" bonus loop in `ascendanteclipsebane.lua`, and the World-Eater's own Enrage fire-rate boost in `ca_worldeater_behavior.lua`. All corrected to `addBaseMultiplier`. This means Eclipse ship damage/stat scaling across the entire mod was likely far weaker in practice than every stated "+X%" comment and tooltip claimed — worth a deliberate playtest pass to confirm the new numbers feel right, since this changes real combat balance, not just a cosmetic value.
- [Bugfix] **`LoadPlanFromFile` Failure Check Used the Wrong Idiom Throughout the Mod (`eclipsegenerator.lua`, all 6 `ca_story0` through `ca_story5` files):** Every one of the 8 call sites that load a `.xml` ship plan and fall back to a generated one on failure checked `if not plan then`, but vanilla's own `factionpacks.lua` — the only vanilla script that checks this call's result at all — uses `if not valid(plan) then`, evidence a failed load may hand back a non-nil-but-invalid object rather than a real `nil`. Currently dormant everywhere it's used (every `.xml` plan this mod ships — `ca_obliterator`, `ca_harbinger`, `ca_voidweaver`, `ca_phantom`, `ca_singularity`, `ca_juggernaut`, `ca_interceptor`, `ca_harvester`, `ca_defiler`, `ca_worldeater`, `ca_citadel`, `ca_aegis`, `ascendancy_anomaly` — is confirmed present on disk), but a plain `nil` check would silently skip the fallback and pass an invalid plan straight into ship/station creation if any plan file is ever renamed or removed. All 8 sites corrected to `valid()`.
- [Bugfix] **`/eclipsestatus` Gave Identical, Unhelpful Output for "Never Triggered" and "Actively Counting Down" (`eclipsestatus.lua`):** The command's very first check, `if not server:getValue("eclipse_fully_awake")`, replied "The Eclipse has not yet awakened" whether the Guardian-kill trigger had never fired at all, or had fired and was legitimately mid-way through its 10-minute awakening countdown — the exact moment this command is most likely to be run by a worried player is also the moment it gave them zero information to act on. Split into two distinct replies using `the_eclipse_unleashed` (this mod's own permanent marker, set the instant the trigger first fires — see the case study on it above): a genuinely untriggered galaxy now says so plainly, while an awakening-in-progress galaxy reports that explicitly (with a rough progress indicator from the `eclipse_warning_1`/`_2` flags) and confirms it resolves on its own. This file had never used `%_T`/`%_t` before and lacked `include("stringutility")` entirely; added it before using either.
- [Cleanup] **Localization Gaps Closed Across the Guardian→Aegis→Eclipse Chain:** `%_T`/`%_t` translation wrapping was applied consistently to every `sendChatMessage`/`broadcastChatMessage` call and dialogue string in `ca_story1_awakening.lua` through `ca_story5_worldeater.lua`, the nested `followUp` dialogue in `ca_ascendant_envoy.lua`'s five debrief functions, and every chat/taunt message in `eclipse_conquest_manager.lua`, `ca_world_eater_manager.lua`, and `ca_worldeater_behavior.lua` — all of which previously sent raw, untranslated strings while `eclipse_awakes.lua` and `ca_story0_meet_aegis.lua` immediately upstream in the same chain already translated everything. Messages built through `..` string concatenation with embedded coordinate variables (rather than a clean literal) were deliberately left as-is, since properly translating those needs a `Format()`/`%1%`-placeholder rewrite, not just a wrapper — noted for a future pass rather than guessed at here. `publishArticle` news content was also left alone, since no news-article call anywhere else in the mod wraps `title`/`content` either — not this pass's convention to invent.
